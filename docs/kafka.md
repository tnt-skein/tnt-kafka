# Очередь Kafka

`tnt-kafka` — клиент Kafka для Tarantool: свой протокол Kafka поверх
встроенного неблокирующего сокета. Тема объявляется вместе с темой
повтора и темой мёртвых, отправка возвращает опознаватель только после
того, как запись легла на все синхронные копии раздела, а получатель —
участник группы — подтверждает сообщение итогом обработчика: значением,
а не вызовом, который можно забыть.

```lua
local kafka = require('tnt.kafka')

local broker = kafka.new({ brokers = { 'kafka-1:9092', 'kafka-2:9092' } })
local orders = broker:declare('orders', { partitions = 6 })  -- и orders.retry, orders.dead

local id, err = orders:send({ order = 7 }, { key = 'customer-42' })  -- ULID после подтверждения

orders:consume(function(message)
    local ok, reason = ship(message.body)

    if not ok then
        return nil, reason                                  -- выдать снова, потом зарыть
    end
end, { workers = 3 })
```

Отказ — пара `nil, err`, где `err` — отказ `tnt-storage` с родом,
признаком отправки и приговором повтору. Исключение — ошибка
программиста: незнакомая настройка, негодное тело, то, чего Kafka
не умеет, отправка внутри транзакции box.

Зависимости: `tnt-must` (проверки аргументов), `tnt-clock` (время
отправки и сроки повтора), `tnt-context` (контекст заголовками), `tnt-id`
(опознаватель ULID), `tnt-log` (журнал), `tnt-pool` (соединения к узлам),
`tnt-retry` (повторы), `tnt-external` (подмена сети, шифрования, сна
и транзакции в проверках), `tnt-storage` (срок вызова и отказ с родом)
и `tnt-tls` (шифрование).

Конверт, итог обработчика, крюки и отказ — общие с очередями `tnt-queue`,
`tnt-event` и `tnt-amqp`: обработчик, написанный под любую из них,
переезжает сюда без правки.

## Зачем пакет

Готового неблокирующего клиента Kafka у Tarantool нет ни в ядре, ни среди
официальных роков, а обёртки над `librdkafka` ждут сети в своих потоках
и отдают итог обратными вызовами мимо файберов. Поэтому протокол написан
поверх встроенного сокета — он неблокирующий и живёт с файберами.
Написан не весь: пакет говорит ровно тем, чем пользуется, — описание
кластера, заведение тем, номер производителя, запись пачкой, выборка,
смещения и группа получателей, плюс вход по SASL PLAIN.

Голый протокол Kafka теряет и повторяет сообщения молча в четырёх местах,
и пакет закрывает каждое:

- **Запись с подтверждением одного узла** пропадает, если узел умер
  до копирования. Здесь запись ждёт всех синхронных копий (`acks = -1`).
- **Повтор записи после обрыва** кладёт её второй раз. Здесь
  производитель идемпотентный: у записи номер в счёте производителя,
  и повтор с тем же номером брокер узнаёт и не пишет.
- **Смещение, зафиксированное до обработки**, теряет сообщение при
  падении обработчика, **зафиксированное пачкой после** — повторяет
  всю пачку. Здесь смещение фиксируется за каждым сообщением, по итогу
  его обработчика.
- **Сообщение, роняющее процесс**, выдаётся после перезапуска снова
  и снова: Kafka выдач не считает. Здесь выдача отмечается до
  обработчика, и после `max_attempts` такое сообщение зарывается,
  не доходя до обработчика.

Сверх протокола пакет ведёт то, чего у Kafka нет: опознаватель сообщения,
номер выдачи, повтор с отсрочкой, зарытые с причиной, срок вызова одним
мигом на всё дело, контекст запроса заголовками и род отказа, по которому
решается, повторять ли вызов.

| Слой | Модуль | Что делает |
|---|---|---|
| значения | `tnt.kafka.wire` | целые старшим байтом вперёд, строки и байты с длиной, числа переменной длины, чтец ответа |
| поля | `tnt.kafka.schema` | запрос и ответ по описанию полей |
| каталог | `tnt.kafka.api`, `tnt.kafka.coordination` | номер и версия запросов, их поля, кадр с шапкой |
| записи | `tnt.kafka.records` | пачка записей второго вида, CRC32C, отсев отменённого в транзакциях |
| коды | `tnt.kafka.codes` | код ошибки брокера → род отказа и что с ним делать |
| связь | `tnt.kafka.link`, `tnt.kafka.connect` | сокет и TLS, запрос и ответ, сверка версий, SASL PLAIN |
| кластер | `tnt.kafka.cluster`, `tnt.kafka.admin` | пулы на узел, описание тем, вызов с повторами, заведение тем |
| отправка | `tnt.kafka.producer`, `tnt.kafka.message` | раздел ключа, счёт записей, конверт |
| группа | `tnt.kafka.offsets`, `tnt.kafka.group` | ведущий группы, смещения, вход, раздача, стук |
| получатель | `tnt.kafka.enter`, `.fetch`, `.handle`, `.worker`, `.outcome`, `.hook` | вход работника, выборка, итог обработчика, крюки |
| тема | `tnt.kafka.topic`, `tnt.kafka.kick` | объявленная тема, возврат зарытых |

## Как пользоваться

### Клиент: `kafka.new`

`kafka.new(opts)` заводит клиента и соединений не открывает: первое
откроет первое дело.

| Ключ | Что | По умолчанию |
|---|---|---|
| `brokers` | узлы для первого знакомства, `host:port`; адрес IPv6 — в скобках | `{ '127.0.0.1:9092' }` |
| `tls` | `true` либо настройки `tnt-tls`: `ca_file`, `ca_path`, `sni`, `verify` | нет |
| `sasl` | `{ username, password, mechanism = 'PLAIN' }` | нет |
| `timeout` | срок вызова, секунд | 5 |
| `max_timeout` | потолок срока вызова, секунд | 60 |
| `max_bytes` | предел длины сообщения и выборки раздела, байт | 1 МБ |
| `session_timeout` | сколько группа ждёт стука участника, секунд | 10 |
| `rebalance_timeout` | сколько группа ждёт участников при раздаче, секунд | 60 |
| `client_id` | чем клиент представляется брокеру | `tnt-kafka` |
| `pool` | настройки `tnt-pool` на каждый узел: `size`, `wait_timeout`… | умолчания пула |
| `retry` | настройки `tnt-retry`: `attempts`, `base`, `factor`, `jitter`, `max` | попытки — до срока вызова |
| `name` | имя клиента в журнале, в имени пула и ведре повторов | `kafka` |

Незнакомый ключ — исключение: опечатка (`pasword`) иначе молча оставила
бы клиента без пароля. Сроки проверяет `tnt-storage`, границы пула
и повторов — сами `tnt-pool` и `tnt-retry`.

Узлы знакомства нужны только чтобы спросить описание кластера: дальше
адреса узлов называет он. Поэтому брокер обязан объявлять адреса,
по которым клиент до него достучится (`advertised.listeners`).

### Объявление: `declare`

```lua
local orders = broker:declare('orders', {
    group = 'mailer',        -- группа получателей; по умолчанию — имя темы
    partitions = 6,          -- разделов у заводимых тем; по умолчанию — брокера
    replication = 3,         -- копий у заводимых тем; по умолчанию — брокера
    shape = order_shape,     -- форма tnt-data: проверка при отправке и на входе получателя
})
```

С темой объявляются **тема повтора и тема мёртвых, и принадлежат они паре
«тема и группа»**: неудачи группы никого, кроме неё, не касаются, а копия
в самой теме досталась бы всем группам, которые её читают. У группы
по умолчанию (её имя — имя темы) это `<тема>.retry` и `<тема>.dead`,
у названной — `<тема>.<группа>.retry` и `<тема>.<группа>.dead`.

Темы заводятся **при первом деле** и **только недостающие**: сначала
описание кластера, и тема, которая есть, не трогается вовсе — учётке
без права заводить темы хватает права писать в готовые. Сам брокер темы
на запись не заводит (`allow_auto_topic_creation` выключен в запросе):
опечатка в имени иначе плодила бы темы с умолчаниями.

Имя темы и группы — буквы, цифры, точка, тире и подчёркивание, как
принимает Kafka; имя темы повтора не длиннее 249 знаков. Негодное имя —
исключение на строке объявления.

### Отправка: `send`

```lua
local id, err = orders:send({ order = 7 }, {
    key = 'customer-42',             -- ключ порядка: раздел по ключу
    headers = { ['x-source'] = 'panel' },
    id = saved_id,                   -- готовый опознаватель: так вывоз ящика шлёт сохранённое
    timeout = 2,
})
```

Опознаватель — ULID, его ставит отправитель: смещение записи у копии
в теме повтора другое, и по нему повтор не отсечь. `send` отдаёт его
после того, как запись подтвердили **все синхронные копии** раздела.

**Раздел ключа — тот же, что у прочих клиентов Kafka**: murmur2 от байтов
ключа без знака по модулю числа разделов. Записи одного ключа от этого
пакета и от чужого производителя ложатся в один раздел, и порядок ключа
держится между ними. Без ключа разделы идут по кругу; раздел выбирается
один раз на отправку и не меняется на повторах.

**Производитель идемпотентный.** Брокер выдаёт номер производителя,
у каждой записи в раздел — свой номер в его счёте, и повтор после обрыва
брокер узнаёт. Поэтому отправка повторяется и после `timeout`, и после
`broken`: без номера в счёте такой повтор положил бы запись второй раз,
а здесь брокер его отсекает. Отправка, бросившая раздел с неизвестным
итогом, оставляет счёт в сомнении, и следующая отправка в тот раздел
берёт новый номер производителя: иначе новая запись с тем же номером
была бы принята за повтор и молча пропала.

Тело — простые данные: `nil`, логика, конечное число, строка, таблица
из них, не глубже ста уровней. Уходит JSON с заголовком `content-type:
application/json`. cdata, функция, бесконечность, кольцо — исключение
при отправке.

**Отправка внутри транзакции box — исключение**: она ждёт брокера,
а уступка порвала бы транзакцию, и сообщение ушло бы и при откате.
«Сохранили и отправили» — через `tnt-outbox`.

### Получатель: `consume`

```lua
local consumer = orders:consume(function(message)
    -- message: id, name, body, headers, key, attempt, created
end, {
    workers = 3,                        -- участников группы в этом процессе
    max_attempts = 5,                   -- после этой выдачи неудача зарывает
    backoff = { base = 1, max = 60 },   -- отступ перед повтором, секунды
})

consumer:stop()                         -- взятое дорабатывается, участники уходят из группы
```

**Работник — участник группы.** Каждый входит в группу сам, получает
долю разделов темы и темы повтора и ведёт их один: подтверждение Kafka —
смещение раздела, накопительное, и два работника на одном разделе
подтверждали бы друг за друга. Раздачу ведёт брокер по кругу
(`roundrobin`): участники по порядку номеров, разделы по порядку тем
и номеров. Та же раздача у прочих клиентов Kafka, и группа, где рядом
стоят чужие получатели, делится между всеми. Работников больше, чем
разделов темы и темы повтора вместе, заводить незачем: лишние стоят
без дела.

Группа, впервые пришедшая к теме, начинает **с начала раздела**: очередь
не теряет того, что отправили до объявления получателя.

Участник стучит своим файбером, пока обработчик работает; стук, услышавший
«идёт раздача» либо «ты вне поколения», велит войти заново, и вход ждёт,
пока взятое сообщение дорабатывается. Обработчик, работающий дольше
`rebalance_timeout`, теряет свои разделы: их отдают другому участнику,
а его итог опоздает (счётчик `late`).

Обработчик — код приложения, и права у него — права фонового файбера,
то есть процесса, а не того, кто объявил получателя. Шаг работника идёт
под `pcall`: сбой считается и пишется, работник живёт дальше.

### Итог обработчика

| Обработчик | Итог |
|---|---|
| вернул значение (не `nil` и не `false`) или ничего | подтвердить: смещение за сообщением |
| вернул `nil, err` или `false, err` | копия в тему повтора с номером выдачи и сроком `retry_after` отказа, иначе отступ `base · 2^(attempt−1)`, не больше `max` |
| выдача номер `max_attempts` не удалась | копия в тему мёртвых с причиной «попыток N из M: …» |
| вернул `nil, err` с `err.retriable == false` | в тему мёртвых сразу |
| бросил исключение | как `nil, err`, причина — текст; пишется `error` со стеком |

**Порядок шагов держит «хотя бы раз».** Сначала отмечается выдача —
фиксируется смещение самого сообщения с числом его выдач, — затем
обработчик, затем копия, и только потом смещение следующего. Обрыв между
любыми двумя шагами оставляет смещение на этом сообщении, и его выдадут
снова; копия, ушедшая до обрыва, уйдёт второй раз с тем же опознавателем.

**Повтор — копией в тему повтора, а не сном на месте**: раздел идёт
дальше, и одно больное сообщение не держит все за собой. Копия несёт
срок `x-tnt-due`; раздел темы повтора, чья голова ждёт срока,
откладывается, а участник идёт к другим разделам.

**Номер выдачи** — `attempt` в конверте: 1 на первой, растёт на каждой
выдаче. Копия несёт номер своей выдачи заголовком, а выдача после
падения — число отметок выдачи со смещением. Сообщение, выданное больше
`max_attempts` раз без итога, зарывается, не доходя до обработчика:
«выдач N при потолке M: прежние выдачи итога не вернули».

Негодное на входе тоже зарывается, не доходя до обработчика: запись,
тело которой не JSON («в теме не конверт tnt-kafka»), и тело не по форме
объявления.

Сжатую пачку чужого производителя пакет прочесть не может (gzip, snappy,
lz4, zstd) и пропускает её со счётчиком `skipped` и записью `error`
с диапазоном смещений. Пачки отменённых транзакций и служебные пачки
отсеиваются: выборка идёт с уровнем «только зафиксированное».

### Зарытые и возврат: `kick`

```lua
local moved, err = orders:kick(10)      -- вернуть до десяти зарытых
```

Возвращённое уходит **в тему повтора** со счётом выдач с нуля: основная
тема досталась бы всем её группам, а зарыла сообщение одна. Тема мёртвых
читается с места, которое помнит своя группа возврата — с именем самой
темы мёртвых. Возврат идёт по одному: взять, записать копию, зафиксировать
смещение; обрыв посреди этого оставляет сообщение в теме мёртвых.

### Признаки: `features`

```lua
kafka.features
--> { key = true, delay = false, ttl = false, ttr = false, touch = false,
--    priority = false, transactional = false, atomic = false }
```

Настройка, которой Kafka не умеет, — исключение, а не молчаливый
пропуск: обработчик, переехавший на Kafka с `delay`, обязан упасть
в проверках, а не начать выдавать сообщения сразу.

| Настройка | Почему нет |
|---|---|
| `delay` | отсрочки у Kafka нет: запись выдаётся, как только легла |
| `ttl` | срок жизни у Kafka один на тему — её хранение, а не у сообщения |
| `priority` | приоритетов нет: раздел выдаётся по порядку смещений |
| `atomic` | смещение фиксируется по сети, а транзакция box уступки не переживает |

### Контекст и заголовки

Отправитель кладёт `context.export()` в заголовки записи в миг `send`,
поверх — заголовки вызывающего. Обработчик идёт в области
`context.run(context.import(headers))`; без `request_id` в заголовках —
свой ULID на сообщение.

Своё пакет несёт заголовками с приставкой `x-tnt-`: `x-tnt-id`,
`x-tnt-attempt`, `x-tnt-created`, `x-tnt-reason` у зарытого и `x-tnt-due`
у копии в теме повтора. Обработчику они не показываются, как и
`content-type`.

### Крюки: `kafka.hook`

```lua
kafka.hook('timing', function(call, proceed)
    local started = clock.monotonic()
    local first, second, third = proceed()

    observe(call.kind, call.name, clock.monotonic() - started)

    return first, second, third
end)
```

`call = { kind = 'send' | 'handle', name, message }`. На отправке конверт
собирается внутри `proceed`, и `traceparent` несёт отрезок, который завёл
крюк; на обработке конверт есть до крюка. Крюки идут снаружи внутрь
в порядке постановки; сорвавшийся крюк ничего не срывает — пишется `warn`,
а `proceed` исполняется один раз. Список крюков — состояние процесса.

### Отправитель для ящика исходящих: `sender`

```lua
outbox.configure({ senders = { ['order.paid'] = broker:sender() } })
```

`sender()` отдаёт таблицу `send(name, body, opts)` и `features`. Имя
назначения — имя темы; не объявленная раньше объявляется умолчаниями
при первой отправке.

### Соединения

У каждого узла кластера свой пул `tnt-pool`: у раздела свой ведущий,
у группы свой ведущий узел, и запись идёт туда. Соединение берётся на одно
дело и возвращается; разговор, сбившийся посреди ответа, выбрасывает его.
Живость свободного соединения проверяется без сети: `sysread` одного
байта у сокета; под TLS — первым же делом.

Описание темы держится до беды: код «ведущий сменился» или «темы нет»
выбрасывает его, и повтор спрашивает заново; без беды — раз в пять минут.
Описание кластера спрашивается у знакомых узлов, затем у узлов знакомства,
и каждому достаётся равная доля оставшегося срока: молчащий узел не съедает
весь срок.

**Версии сверяются при входе** (`ApiVersions`): брокер, которому пришла
незнакомая версия, закрывает соединение, и это выглядело бы обрывом
сети. Пакет говорит версиями без «гибкой» записи и не ниже тех, что
принимают выпуски брокера 4.x; не принятая версия — отказ входа
`rejected` с именем запроса и границами.

### Вход и шифрование

```lua
local broker = kafka.new({
    brokers = { 'kafka-1:9093' },
    tls = { ca_file = '/etc/ssl/kafka-ca.pem' },
    sasl = { username = 'app', password = secret },
})
```

Вход — только SASL PLAIN: брокер называет свои способы, и нет среди них
PLAIN — отказ `denied`. Пароль уходит строкой `\0имя\0пароль` в открытом
виде, поэтому TLS здесь не украшение. Неверная пара «имя и пароль» —
`denied` без повтора: пул не стучится с тем же паролем.

`tls = true` берёт умолчания `tnt-tls`. Проверка сертификата включена
по умолчанию; `verify = false` — осознанный выбор вызывающего.

### Отказ

| Род | Когда |
|---|---|
| `unreachable` | узел не открылся, вход не завершился, ведущего нет, ведущий сменился, копий не хватает, группу ведёт другой узел |
| `denied` | не тот пароль, нет PLAIN, нет прав на тему, группу или кластер |
| `busy` | за срок не досталось соединения либо раздел занят другой записью |
| `timeout` | брокер не ответил за срок вызова |
| `broken` | связь оборвалась, ответ не разобран, незнакомый код брокера |
| `rejected` | брокер не принял запись (длина, негодная запись), не принял версию, не завёл тему |
| `conflict` | участник выпал из поколения группы: идёт раздача |
| `closed` | клиент закрыт |

Повторяет вызов `tnt-retry` по полю `retriable` — до срока вызова, а не
три раза: ведущий раздела сразу после заведения темы и после смены узла
готов через сотни миллисекунд. Код брокера лежит в `server_code`.

### Состояние и счётчики: `status`

```lua
local status = broker:status()      -- клиент: name, closed, pools, topics, hooks
local counts = orders:status()      -- тема: name, group, retry, dead, counts, workers, hooks
```

| Счётчик темы | Что считает |
|---|---|
| `sent` | отправлено и подтверждено копиями |
| `ack` | подтверждено обработчиком |
| `retry` | ушло в тему повтора |
| `bury` | зарыто |
| `late` | итог не дошёл до брокера: сообщение выдадут снова |
| `failures` | сбоев шага, входа и отметки выдачи |
| `skipped` | пропущено сжатых пачек |
| `kicked` | возвращено из темы мёртвых |

### Журнал

Записи идут в журнал `tnt.kafka`:

| Запись | Уровень |
|---|---|
| `сообщение зарыто`, `обработчик сообщения бросил` — с текстом и стеком | `error` |
| `пачка сжата, и прочесть её нечем: записи пропущены` | `error` |
| `итог обработчика не дошёл до брокера: сообщение выдадут снова`, `выдача сообщения не отмечена` | `warn` |
| `смещение раздела вне журнала: непрочитанное стёрто хранением темы` | `warn` |
| `вход в группу не удался`, `выборка не удалась`, `шаг работника получателя сорвался`, `крюк очереди сорвался и пропущен` | `warn`, с подавлением повторов |
| `участник вошёл в группу` | `info` |
| `сообщение выдадут снова` | `debug` |

Тело сообщения в журнал не пишется: в нём бывают персональные данные.

### Подмена в проверках

| Модуль | Внешние зависимости |
|---|---|
| `tnt.kafka.link` | `dial(host, port, timeout)` — сокет; `cipher(socket, opts)` — TLS поверх него |
| `tnt.kafka.worker`, `.enter`, `.fetch` | `sleep(seconds)` — паузы после сбоя |
| `tnt.kafka.topic` | `in_txn()` — идёт ли транзакция box |

Часы срока вызова — у `tnt.storage.within` (`monotonic`, `scheduler_now`).

```lua
local link = require('tnt.kafka.link')

link._set_source({
    dial = function()
        return nil, 'сети нет'
    end,
})

local id, err = broker:declare('orders'):send('письмо')
--> nil, err.kind == 'unreachable', err.message: «… соединение не открылось: сети нет»

link._set_source(nil)
```

## Чем пришлось поступиться

- **Повтор ломает порядок ключа.** Копия уходит в тему повтора, и
  следующие сообщения того же ключа обработаются раньше повторённого.
  Цена того, что одно больное сообщение не держит раздел.
- **Голова темы повтора ждёт срока.** Отступ растёт с номером выдачи,
  и копия с коротким сроком, стоящая за копией с длинным, ждёт её.
- **Две фиксации на сообщение.** Отметка выдачи перед обработчиком —
  плата за то, что сообщение, роняющее процесс, не ходит по кругу.
- **Одна запись в пачке и одна запись в раздел разом.** Брокер ждёт
  номера производителя строго по порядку, и следующая отправка в тот же
  раздел ждёт ответа на предыдущую. Накопления записей в пачку нет.
- **Сжатые пачки не читаются** — пропускаются со счётом и записью.
- **Только SASL PLAIN.** Входа SCRAM и по сертификату нет, сертификата
  клиента драйвер не предъявляет: настройка `tls` не передаёт его
  в `tnt-tls`.
- **Раздача только по кругу.** Липкой раздачи, которая сохраняет разделы
  за участником через раздачу, нет: после каждой раздачи участник
  начинает свои разделы с зафиксированного смещения.
- **Сроки повтора — стенные часы.** Срок `x-tnt-due` пишется стенным
  временем отправителя копии: перевод часов назад продлевает отсрочку,
  вперёд — обрывает её.
- **Восьмибайтовые целые — числом Lua.** Смещение, отметка времени
  и номер производителя точны до 2^53 — на практике недостижимо, но
  предел назван.

## Проверки

Проверки лежат в `test/` и идут на luatest: `.rocks/bin/luatest test/`.
Протокол проверяется двойником брокера на настоящем сокете: он заводит
темы, выдаёт номер производителя и сверяет счёт его записей, кладёт
пачки в журнал раздела и отдаёт их выборкой, ведёт группы кругами входа,
раздачу, стук и смещения. Чего двойник не умеет — отказ, молчание,
обрыв, — задаёт проверка ответом на пришедший запрос. Отказ отправки
внутри транзакции проверяется на настоящем узле (`txn_node_test.lua`):
в процессе проверок `box` не настроен.

Живая проверка `kafka_live_test.lua` идёт против Kafka 3.9 в докере
(один узел KRaft): отправка и получение с контекстом и ключом, раздел
ключа, повтор, зарытое и возврат, два работника в группе, названная
группа, SASL PLAIN с верным и неверным паролем, TLS с сертификатом стенда
и без доверия к нему.

```sh
make kafka-up                                   # порты 19092, SASL 19094, TLS 19095
.rocks/bin/luatest test/kafka_live_test.lua
make kafka-down
```

Без поднятого брокера живые проверки пропускаются: гейты не зависят
от докера. Покрытие строк — 100 %.
